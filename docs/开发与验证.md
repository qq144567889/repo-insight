# 开发与验证

## 开发

**没有构建步骤**：源码即产物。修改后在 `chrome://extensions` 点刷新即可生效（改了 `background.js` 建议在扩展卡片点「Service Worker」查看日志）。

调试入口：

- 弹窗：右键扩展图标 → 检查弹出内容；
- 后台：`chrome://extensions` → 本扩展 → 点「Service Worker」；
- 部署页 / 设置页：普通标签页，直接 F12。

## 打包

```bash
bash tools/package.sh          # 输出 repo-insight-<version>.zip，并在打包后自检
python3 tools/gen_icons.py     # 重新生成 16 / 48 / 128 图标
```

打包自检会解析所有 HTML 的 `src`/`href` 与 JS 的 `import`，确认被引用的文件都在包内，缺文件直接失败——避免"装上去功能打不开"。

## 验证体系

项目采用三层验证，均可在本机复现：

| 层级 | 规模 | 覆盖内容 |
|---|---|---|
| 静态与单元检查 | 400+ 项 | 清单完整性与图标尺寸、JS 引用的 DOM id 是否真实存在、无内联脚本 / 无 `eval` / 无 `innerHTML`、URL 解析正反例、许可证分级、脱敏与掩码、文件名清洗、部署脚本生成、深浅色主题变量是否被三个界面引用 |
| 编排层用例 | 100+ 项 | 用假 `chrome` + 假 `fetch` 跑**真实 background.js**：缓存命中、私有仓库拦截时零外发、403 限流分流、降级路径、历史生命周期与导出脱敏、流式分片、自动弹出触发与去重 |
| 真实浏览器验证 | 90+ 项 | 在真实 Chrome 中加载扩展：清单本地化、弹窗渲染、真实抓取 GitHub、模型链路（本地 mock 服务）、流式增量渲染、历史恢复、部署页风险评估与勾选闸门、深浅色配色比对 |

补充验证：

- 生成的 shell 脚本都会过 `bash -n` 语法校验；
- **只读环境检测脚本会被实际执行**，检查其输出的 JSON 可被解析、并转成预检表格；
- 部署脚本以 `--dry-run` 实际执行，验证缺 Docker 时能给出安装指引并退出。

## 复现方式

验证脚本本身不进仓库（它们是开发期工具），如果你想自行复现，可以按下列思路搭建：

1. **静态检查**：写一个 Node 脚本，读取 `manifest.json` 与各 HTML/JS，断言文件存在、DOM id 对应、无危险 API；
2. **编排层**：在 Node 里伪造 `globalThis.chrome`（`storage.local/session`、`runtime.onMessage/onConnect`、`tabs.onUpdated`、`action.*`）与 `globalThis.fetch`，然后 `await import('./background.js')`，通过触发监听器调用真实逻辑；
3. **真实浏览器**：用 Chrome 的 `--remote-debugging-port` + CDP，通过 `Extensions.loadUnpacked` 加载扩展（注意：Google 官方版 Chrome 从 137 起禁用了命令行 `--load-extension`），再对扩展页面执行 `Runtime.evaluate` 断言。

## 已知限制

- 官方版 Chrome 不允许命令行加载未打包扩展，自动化验证走 CDP 的 `Extensions.loadUnpacked`；
- headless 环境下动作弹窗（`chrome.action.openPopup()`）可能返回 `Failed to open popup.`，涉及真实弹窗窗口的用例会被标记为跳过并说明原因；
- 无头环境下 `github.com` 页面有时加载缓慢，依赖页面 `complete` 事件的用例会显式跳过，而不是伪装成通过。

## 提交代码前建议自查

- [ ] `manifest.json` 合法，未新增高危权限；
- [ ] 所有新增的 `.js` / `.css` / `.html` 文件保留头部署名注释；
- [ ] 未在代码中写死任何密钥、Token、真实示例 Key；
- [ ] 新增用户可见文案时，考虑深浅色两种模式下的可读性；
- [ ] 改动提示词时同步递增 `lib/prompt.js` 的 `SYSTEM_PROMPT_VERSION`，并复核 `docs/输出模板.md`。
